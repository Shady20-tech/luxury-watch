# Database schema — Luxury Watch Storefront & Administration Platform

This document describes the schema that actually exists in `supabase/migrations/`,
verified against a real PostgreSQL 17 instance. Every table, constraint, policy and
function named here was read back from the running database, not from an intention.

Companion documents: `ARCHITECTURE.md` (§5 data model, §7 security boundaries),
`IMPLEMENTATION_PLAN.md` (phases), `KNOWN_ISSUES.md` (open items).

---

## 1. How to work with the schema

### 1.1 Apply migrations

Migrations are numbered and applied in filename order. They are written to be safe
on a fresh database and to be re-runnable in a disposable test environment.

```bash
# Supabase CLI (linked project)
supabase db push

# Or directly, against any Postgres
for f in supabase/migrations/*.sql; do
  psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f"
done
```

| File | Contents |
|---|---|
| `0001_extensions_enums_helpers.sql` | `pgcrypto`, `citext`, 13 enum types, `set_updated_at()`, `normalize_slug()`, order-reference sequence and generator |
| `0002_accounts_profiles_roles.sql` | `profiles`, `user_roles`, `addresses`, new-user trigger |
| `0003_catalogue.sql` | `brands`, `models`, `products`, `product_images`, `product_specs`, `collections`, `collection_products`, `inventory`, `inventory_transactions` |
| `0004_commerce.sql` | `payment_methods`, `delivery_options`, `carts`, `cart_items`, `order_requests`, `order_request_items`, `order_request_events`, `inventory_reservations` |
| `0005_service_requests.sql` | `inquiries` and every service flow, `appointments`, `contact_submissions`, `product_questions`, `messages`, `notifications` |
| `0006_content_and_config.sql` | `pages`, `faqs`, `announcements`, `testimonials`, `navigation_items`, `homepage_sections`, `media`, `site_settings`, `newsletter_subscribers`, `admin_audit_logs`, `rate_limit_counters` |
| `0007_rls_policies.sql` | Role helpers, the permission map, RLS enabled on all 47 tables, 96 policies |
| `0008_order_submission_and_reservations.sql` | `reserve_inventory`, `release_reservation`, `confirm_reservation`, `submit_order_request`, status-change trigger |

### 1.2 Verify locally

Three scripts exist so the schema can be proven without a Supabase account. They
auto-detect whether Docker needs `sudo`.

```bash
scripts/db-reset.sh          # drop and recreate the schema, then re-apply the shim
scripts/db-verify.sh         # apply the shim + all 8 migrations, then run the test suite
scripts/db-concurrency-matrix.py   # the five-scenario inventory proof (see §7)
```

`db-verify.sh` expects a running Postgres. To create one:

```bash
docker run -d --name lw-pg-test -e POSTGRES_PASSWORD=postgres -p 55432:5432 postgres:17-alpine
```

`supabase/tests/00_supabase_shim.sql` emulates the parts of a Supabase project that
the migrations depend on: the `auth` schema with `auth.users` and `auth.uid()`, and
the `anon`, `authenticated` and `service_role` roles. **It is a test fixture, not a
deployment artifact.** On real Supabase those already exist and the shim is not used.

### 1.3 Regenerate the TypeScript types

`src/lib/database.types.ts` is generated from the live schema and must be
regenerated after every migration:

```bash
npx supabase gen types typescript \
  --db-url "$DATABASE_URL" --schema public > src/lib/database.types.ts
```

Note the `?sslmode=disable` suffix if you are pointing at a local container over a
plain TCP connection — without it the generator refuses the connection.

The file is listed in `.prettierignore` and `eslint.config.mjs`, so the generator's
formatting survives and a regeneration produces a clean diff. Never hand-edit it.

### 1.4 Seed the development catalogue

```bash
psql "$DATABASE_URL" -f supabase/seed/01_catalogue.sql
```

The seed is generated by `scripts/generate-catalogue-seed.py` from the reference
harvest. See §9 for exactly what it does and does not contain.

## 3. Tables

47 tables in `public`. Grouped by concern.

### 3.1 Accounts and authorisation

**`profiles`** — one row per `auth.users` row, created by the `on_auth_user_created`
trigger. Columns: `id` (PK, FK to `auth.users.id`), `email`, `full_name`, `phone`,
`avatar_url`, `marketing_opt_in`, `created_at`, `updated_at`.

> **There is no `role` column on `profiles`.** Phase 0 planned one; Phase 2 moved
> roles into a separate `user_roles` table instead. The reason is in §6.1: a role
> column on a row the user can update is one policy mistake away from privilege
> escalation. Splitting the tables makes self-escalation structurally impossible
> rather than merely forbidden, because there is no column for the client to write.

**`user_roles`** — `id`, `user_id` → `profiles`, `role` (`staff_role`), `granted_by`,
`granted_at`, `expires_at` (nullable). Unique on `(user_id, role)`. `expires_at`
lets a temporary grant lapse without a manual revoke; every helper ignores expired
rows.

`staff_role` enum: `SUPER_ADMIN`, `ADMIN`, `SALES_MANAGER`, `INVENTORY_MANAGER`,
`WATCH_EXPERT`, `CUSTOMER_SUPPORT`, `CONTENT_MANAGER`.

**`addresses`** — `id`, `user_id`, `label`, `recipient_name`, `line1`, `line2`,
`city`, `region`, `postal_code`, `country_code`, `phone`, `is_default`,
`created_at`, `updated_at`. One default per user is enforced by a partial unique
index.

### 3.2 Catalogue

**`brands`** — `id`, `name`, `slug` (unique), `description`, `logo_url`,
`hero_image_url`, `founded_year`, `country_of_origin`, `seo_title`,
`seo_description`, `is_active`, `sort_order`, timestamps.

**`models`** — `id`, `brand_id` → `brands`, `name`, `slug`, `description`,
`is_active`, `sort_order`. Unique on `(brand_id, slug)`. This is the two-level
Brand → Model taxonomy the reference site uses.

> There is no `categories` table. Phase 0 listed one as "optional cross-cutting
> grouping"; nothing in the reference navigation or the storefront needs it, and
> `collections` already covers curated groupings. Adding an unused table would be
> scaffolding without a consumer.

**`products`** — 34 columns. Identity (`sku` unique, `slug` unique, `title`),
taxonomy (`brand_id`, `model_id`), description (`description`, `short_description`),
attributes (`condition`, `production_year`, `reference_number`, `case_size_mm`,
`case_material`, `movement`, `dial_color`, `bracelet_material`, `bezel`,
`water_resistance_m`, `gender`, `box_and_papers`), pricing (`price_cents`,
`currency`, `compare_at_cents`, `cost_cents`, `price_on_request`), state (`status`,
`is_featured`, `published_at`, `sort_order`), SEO (`seo_title`, `seo_description`,
`seo_keywords`, `og_image_url`), timestamps.

**`product_images`** — `id`, `product_id`, `storage_path` **or** `external_url`
(exactly one, enforced by `product_images_source_exclusive`), `alt_text`,
`width`, `height`, `sort_order`, `is_primary`, timestamps.

**`product_specs`** — `id`, `product_id`, `label`, `value`, `sort_order`. The
flexible label/value table for attributes that do not warrant a column.

**`collections`** — `id`, `title`, `slug`, `kind` (`collection_kind`), `description`,
`hero_image_url`, SEO fields, `is_active`, `sort_order`, timestamps.

**`collection_products`** — `collection_id`, `product_id`, `sort_order`. Composite PK.

**`inventory`** — `id`, `product_id` (unique, 1:1), `quantity`,
`reserved_quantity`, `low_stock_threshold`, `location`, `updated_at`.

**`inventory_transactions`** — the append-only stock ledger. `id`, `product_id`,
`kind` (`inventory_transaction_kind`), `quantity_delta`, `reserved_delta`,
`order_request_id`, `actor_id`, `note`, `created_at`.

`inventory_transaction_kind`: `acquisition`, `adjustment`, `reservation`,
`reservation_release`, `sale`, `return`, `correction`.

### 3.3 Commerce — no payments

**`payment_methods`** — `id`, `code` (unique, format-checked lowercase snake),
`label`, `description`, `instructions`, `is_enabled`, `sort_order`, timestamps.
This is an administrator-controlled list of **offline** options. It stores no
credential, no gateway reference and no token. `instructions` holds the text shown
to the customer, e.g. the bank details to transfer to.

**`delivery_options`** — `id`, `code`, `label`, `description`, `fee_cents`,
`is_enabled`, `sort_order`, timestamps.

**`carts`** / **`cart_items`** — `carts` has `id`, `user_id` (nullable),
`session_token`, `currency`, timestamps, with a check that at least one owner
exists. `cart_items` has `cart_id`, `product_id`, `quantity`, `unit_price_cents`.

**`order_requests`** — the core commerce record. 23 columns: `id`, `reference`
(unique, `LW-YY-NNNNNN`), `user_id` (nullable for guests), `customer_name`,
`customer_email`, `customer_phone`, `fulfilment_type` (`delivery`/`pickup`),
`delivery_address` (jsonb), `pickup_location`, `payment_method_code`,
`customer_note`, `admin_note`, `subtotal_cents`, `delivery_fee_cents`,
`total_cents`, `currency`, `status`, `settled_offline_at`, `settled_offline_by`,
`ip_hash`, `user_agent`, timestamps.

`order_status`: `submitted`, `under_review`, `confirmed`, `awaiting_payment`,
`paid_offline`, `fulfilled`, `cancelled`, `rejected`.

> **There is no `paid` status, and no status a customer can set.** `paid_offline`
> is reachable only by an administrator, and only after verifying payment outside
> the website. There is no schema path from "customer submitted a form" to
> "payment received".

**`order_request_items`** — `order_request_id`, `product_id` (nullable, so a later
product deletion does not destroy order history), `product_title_snapshot`,
`sku_snapshot`, `unit_price_cents` (nullable for price-on-request),
`quantity`, `line_total_cents`.

**`order_request_events`** — append-only status history: `order_request_id`,
`actor_id`, `from_status`, `to_status`, `note`, `created_at`.

**`inventory_reservations`** — `id`, `product_id`, `order_request_id`, `quantity`,
`expires_at`, `is_active`, `released_at`, `created_at`.

### 3.4 Service requests

`inquiries` (`type`: `sell_trade`, `sourcing`, `repair`, `general`,
`product_question`; `status`: `new`, `in_review`, `responded`, `closed`, `spam`),
`inquiry_replies`, `sell_trade_requests`, `sell_trade_images`, `sell_trade_offers`,
`sourcing_requests`, `sourcing_updates`, `repair_requests`, `repair_updates`,
`appointments`, `contact_submissions`, `product_questions`, `messages`,
`notifications`.

Each flow has a parent request table, an append-only update/reply table, and RLS
that lets the submitter read their own thread and staff read all of it.

### 3.5 Content and configuration

`pages`, `faqs`, `announcements`, `testimonials`, `navigation_items`
(`location`: `header`, `footer`, `topbar`), `homepage_sections`, `media`,
`site_settings` (22 columns; singleton enforced by a single-row constraint),
`newsletter_subscribers`, `admin_audit_logs`, `rate_limit_counters`.

**`newsletter_subscribers`** carries a `token` column defaulted to
`encode(extensions.gen_random_bytes(32), 'hex')` for confirmation and unsubscribe
links. The `extensions.` qualifier is required because Supabase installs `pgcrypto`
into a separate `extensions` schema, not `public`.

**`admin_audit_logs`** is append-only: there is a `SELECT` policy and no `INSERT`,
`UPDATE` or `DELETE` policy for any API role. Only the service role can write it.

## 5. Constraints that carry business meaning

These are not incidental validations. Each one makes a class of bug impossible
rather than merely unlikely, and each is covered by a test.

| Constraint | Table | What it prevents |
|---|---|---|
| `products_price_consistency` | products | A product that is `price_on_request` but also has a price, or vice versa. Exactly one representation is valid. |
| `products_published_requires_timestamp` | products | A published product with no `published_at`, which would break the sitemap's `<lastmod>`. |
| `inventory_quantity_non_negative` | inventory | Negative stock from any code path. |
| `inventory_reserved_within_quantity` | inventory | Over-reservation. This is the second of the two independent defences described in §7. |
| `inventory_reserved_non_negative` | inventory | A negative hold, which would silently inflate availability. |
| `inventory_transactions_quantity_delta_nonzero` | inventory_transactions | A no-op ledger entry. |
| `order_requests_total_matches_parts` | order_requests | A total that disagrees with `subtotal + delivery_fee`. |
| `order_requests_fulfilment_details` | order_requests | Delivery with no address. |
| `order_requests_settlement_complete` | order_requests | A settlement timestamp with no recording administrator, or the reverse. Both fields are set together or neither is. |
| `order_requests_amounts_non_negative` | order_requests | Negative money. |
| `payment_methods_code_format` | payment_methods | Arbitrary codes reaching the storefront. |
| `delivery_options_fee_non_negative` | delivery_options | A negative delivery fee. |
| `product_images_source_exclusive` | product_images | An image with both a `storage_path` and an `external_url`, or neither. |
| `product_images_alt_required` | product_images | A missing `alt_text`, which would fail the accessibility target. |
| `carts_owner_present` | carts | A cart with neither a user nor a session token, which could never be retrieved. |
| `addresses_country_code_format` | addresses | A malformed country code. |

## 6. Authorisation

### 6.1 Why roles live in their own table

The Phase 0 architecture put `role` on `profiles`. Phase 2 changed that. The
reasoning:

A customer must be able to update their own profile — name, phone, avatar. If
`role` sits on that same row, then the security of the entire application rests on
the profile `UPDATE` policy correctly excluding the `role` column. PostgreSQL RLS
cannot restrict *columns*; it can only restrict rows. A policy that allows
`UPDATE` on your own profile allows updating every column of it. The usual
mitigations — a `WITH CHECK` clause comparing `role` to its old value, or a trigger
rejecting role changes — both work, but both are single points of failure guarding
the highest-value column in the schema.

Moving roles to `user_roles`, which has no insert, update or delete policy for
ordinary users, removes the column from the writable surface entirely. There is
nothing to protect, because there is nothing to write. The test
`supabase/tests/30_role_escalation.sql` asserts this directly: an attempt to
`update public.profiles set role = 'ADMIN'` fails at parse time, because no such
column exists.

### 6.2 The helper functions

All are `SECURITY DEFINER` with `set search_path = ''` and fully-qualified
references, so they cannot be redirected by a hostile `search_path`.

| Function | Returns | Meaning |
|---|---|---|
| `public.is_staff()` | boolean | The caller holds any unexpired staff role. |
| `public.is_admin()` | boolean | The caller is `ADMIN` or `SUPER_ADMIN`. |
| `public.has_role(role)` | boolean | The caller holds this specific unexpired role, or is `SUPER_ADMIN` (which satisfies every role). |
| `public.has_permission(permission)` | boolean | The caller's roles grant this permission, or the caller is `SUPER_ADMIN`. |
| `public.role_permissions(role)` | text[] | The permission list for a role, from a static map. |

Permissions are named `domain.action`: `catalog.write`, `inventory.write`,
`orders.read`, `orders.write`, `orders.settle`, `content.write`, `audit.read`,
`roles.assign`, and so on. `has_permission` is the primitive the service layer and
the RLS policies both call, so a rule stated once cannot drift between them.

### 6.3 The RLS posture

Every one of the 47 tables has `relrowsecurity = true`. There are 96 policies.

The design is **default deny with a small explicit public surface**:

- A table with no policy grants nothing to `anon` or `authenticated`.
- Anonymous visitors can read only what the storefront genuinely needs: active
  brands and models, published products, their images and specs, active
  collections, published pages and FAQs, enabled payment and delivery options,
  active navigation and homepage sections, published testimonials and
  announcements.
- Disabled payment methods are invisible, so the storefront cannot offer one by
  accident even if a query forgets the filter.
- Customers can read and write only rows they own. `addresses`, `carts`,
  `wishlists` and their own `order_requests` are scoped by `auth.uid()`.
- Customers cannot insert an `order_requests` row directly. The only path is the
  `submit_order_request` RPC, which re-prices server-side. A direct insert is
  denied, and there is a test for it.
- Staff policies are gated on `has_permission(...)`, never on client-supplied
  metadata.
- `admin_audit_logs` is readable by `has_permission('audit.read')` and writable by
  nobody through the API, including `SUPER_ADMIN`.

### 6.4 The authorisation tests

`supabase/tests/` contains four suites, run by `scripts/db-verify.sh`:

| File | What it proves |
|---|---|
| `00_supabase_shim.sql` | Test fixture: `auth.users`, `auth.uid()`, the API roles. Not a deployment artifact. |
| `10_public_boundary.sql` | Anonymous visitors read the published catalogue and nothing else. Covers 20 private tables, and confirms the published product *is* readable so the denials are not vacuous. |
| `20_customer_ownership.sql` | One customer cannot read another's data. Internal notes stay hidden even on the customer's own record. A customer cannot rewrite the commercial facts of their own order. |
| `30_role_escalation.sql` | The decisive test: no customer can grant themselves a role. Also verifies each staff role's permission boundary, that `ADMIN` is not `SUPER_ADMIN`, that an expired role grants nothing, and that the audit log resists even `SUPER_ADMIN`. |
| `40_order_and_inventory.sql` | Server-derived totals, price-on-request recording no amount, disabled payment methods rejected, inventory unable to go negative, reject releasing stock, confirm converting a hold into a sale, and a schema-wide assertion that no column can hold card data. |

The suites share one database, so "can read" is asserted as "sees at least one
row" and "cannot read" as "sees exactly zero". That asymmetry is deliberate: the
strict assertion is on the denial, which is the security property.

## 7. Inventory safety under concurrency

Two units of stock must not be sold twice. Two independent mechanisms enforce
this, and `scripts/db-concurrency-matrix.py` proves each one works on its own.

**Mechanism 1 — the row lock.** `reserve_inventory()` selects the inventory row
`for update`, which serialises the read-check-write cycle. A second transaction
blocks until the first commits, then re-reads the updated `reserved_quantity` and
correctly refuses.

**Mechanism 2 — the check constraint.** `inventory_reserved_within_quantity`
rejects any write where `reserved_quantity > quantity`, at the storage layer. Even
a code path that skips the lock cannot over-reserve.

The proof matrix runs five scenarios against real Postgres, launching eight
concurrent order submissions for a product with exactly one unit in stock:

| Scenario | Protections | Result | What it shows |
|---|---|---|---|
| 1 | lock + constraint | HOLDS | The normal path is correct. |
| 2 | lock + constraint, widened window | HOLDS | Correct under genuine contention, not just by luck of timing. |
| 3 | constraint only | HOLDS | The constraint alone is sufficient. |
| 4 | lock only | HOLDS | The lock alone is sufficient. |
| 5 | neither | **BREAKS** | 8 of 8 racers succeeded, `reserved_quantity` reached 8 and available stock went to −7. |

Scenario 5 is the important one. Without it, a green result would be
indistinguishable from a test that does nothing.

> **How this test was made honest.** The first version of it passed even with the
> row lock removed, which meant it was proving nothing: the critical section runs
> in microseconds, so eight processes almost never overlapped inside it. It also
> did not actually run the racers concurrently at all — `docker exec -i` attaches
> stdin, so backgrounded jobs received `SIGTTIN` and were suspended rather than
> racing. The current version launches every racer as a separate process before
> waiting on any of them, and `--slow-window` inserts a deliberate delay between
> the read and the write so overlap is certain rather than hoped for. The
> negative-control modes exist so the test can be shown to fail. This is recorded
> in `KNOWN_ISSUES.md` history because it is the kind of mistake that makes a test
> suite untrustworthy.

## 8. Order-request flow at the database level

The storefront never inserts order rows directly. `submit_order_request(...)` is
the single entry point, and it is `SECURITY DEFINER` so it can write on behalf of
an anonymous customer while still enforcing every rule:

1. Validates the payload — non-empty item list, positive quantities, required
   contact fields, and that the fulfilment type's details are present.
2. Resolves the payment method by code and **refuses if it is not enabled**. A
   disabled or unknown method is an error, not a silent default.
3. Resolves the delivery option and refuses if it is not enabled.
4. Re-reads every product from the database. Only `published` products can be
   ordered. A draft product id is rejected even if the caller supplies it directly.
5. **Recomputes prices server-side** from `products.price_cents`. A price sent by
   the client is ignored. Price-on-request products contribute zero and their line
   stores a null `unit_price_cents`.
6. Computes `subtotal + delivery_fee = total`, which the
   `order_requests_total_matches_parts` constraint then re-verifies.
7. Creates the order as `submitted`, snapshots each line, and writes the opening
   `order_request_events` row.
8. Reserves inventory for each line via `reserve_inventory()`. If any line cannot
   be reserved, the whole transaction rolls back — there is no partial order.

Status transitions are handled by `handle_order_status_change`, which releases the
reservation on `rejected` or `cancelled` and converts it to a sale on `confirmed`.
`settled_offline_at` and `settled_offline_by` can only be set together, by an
administrator, and never by submission.

## 9. The development seed

`supabase/seed/01_catalogue.sql` is generated by
`scripts/generate-catalogue-seed.py` from a harvest of the reference catalogue:
4110 products across 4 brands and 41 model families, with 8785 specification rows.

**What is included.** Factual attributes of physical objects: brand, model family,
product name, reference number, case size and material, movement, dial colour,
bracelet, bezel, water resistance, gender, box-and-papers, condition.

**What is deliberately excluded, and why.**

1. **Images.** No `product_images` rows are seeded. The reference site's CDN assets
   are copyrighted, and hotlinking them would be both a licensing problem and a
   broken-image problem. Real photography must be added through the admin or
   uploaded to Supabase Storage.
2. **Marketing prose.** `description` is left null. The reference site's text is
   its own content. Attributes are stored as `product_specs` rows instead, which is
   what a product page actually needs to render a specification table.
3. **Prices.** Every product is seeded `price_on_request = true` with a null price,
   matching how the reference catalogue presents itself. Real prices must be set in
   the admin.
4. **Trademark claims.** Brand names appear as factual attribution only. Nothing
   claims authorised-dealer status or manufacturer endorsement.

**Safety properties.** Every product is inserted with `status = 'draft'`, so
nothing is visible on the storefront until an administrator publishes it
deliberately. The seed is idempotent — re-running updates by slug rather than
duplicating, and `inventory` uses `ON CONFLICT DO NOTHING` so it never resets stock
that has since been adjusted. It is development data and must not be run against a
production database that holds real records.

## 10. Indexes

138 indexes. Beyond primary keys and unique constraints, the notable ones:

**Catalogue and storefront**

- `products_status_published_idx` — `(status, published_at desc)`. Drives the
  storefront listing and the sitemap query.
- `products_search_idx` — GIN on `to_tsvector('english', title || reference_number
  || short_description || case_material || dial_color)`. Catalogue search.
- `products_featured_idx` — partial, `where is_featured`.
- `products_price_idx` — partial, `where price_cents is not null`. Excludes
  price-on-request rows, which are a large share of the catalogue.
- `product_images_product_sort_idx`, `product_specs_product_idx` —
  `(product_id, sort_order)`, for rendering a product page in one pass.
- `brands_slug_key`, `products_slug_key` — unique, so a slug is a valid lookup key
  and the sitemap cannot emit duplicate URLs.

**Commerce**

- `order_requests_user_idx` — `(user_id, created_at desc)`. A customer's history.
- `order_requests_status_idx` — `(status, created_at desc)`. The admin queue.
- `order_requests_email_idx` — supports the guest lookup, which requires the exact
  reference *and* the email.
- `order_requests_reference_key` — unique.
- `inventory_transactions_product_idx` — `(product_id, created_at desc)`. The
  stock ledger.
- `inventory_reservations_active_key` — **partial unique** on
  `(order_request_id, product_id) where is_active`. This is a third structural
  guard on the reservation path: it makes it impossible for one order to hold two
  active reservations for the same product, independently of the lock and the
  constraint described in section 7.
- `inventory_reservations_product_idx` — partial, `where is_active`, for the
  availability calculation.

**Accounts and content**

- `addresses_one_default_per_user_idx`, `wishlists_one_default_per_user_idx` —
  partial unique on `(user_id) where is_default`. At most one default per user,
  enforced by the index rather than by application code.
- `carts_user_key`, `carts_session_key` — partial unique, so one cart per signed-in
  user and one per guest session.
- `product_images_one_primary_idx` — partial unique on `(product_id) where
  is_primary`. A product cannot have two primary images.
- `newsletter_subscribers_email_key`, `newsletter_subscribers_token_key` — unique.
- `admin_audit_logs_created_idx`, plus actor and entity indexes for the audit view.
- `inquiries_assigned_idx` — partial, `where assigned_to is not null`.

The partial indexes are not micro-optimisation. Several of them — the one-default
constraints, the single-primary-image constraint, and
`inventory_reservations_active_key` — are the enforcement mechanism for a rule that
would otherwise need application code to get right on every path.

## 11. What this schema cannot express

By construction, not by policy:

- **No online payment.** No table has a column for a card number, PAN, CVV, expiry,
  IBAN, payment token, payment intent or provider reference. No enum has a
  "paid online" state. `supabase/tests/40_order_and_inventory.sql` asserts this
  across `information_schema.columns`, so a future migration that adds such a
  column fails the test suite. The CI guard
  `scripts/check-no-payment-providers.mjs` independently fails the build on a
  payment SDK, webhook route or card field.
- **No customer-reachable paid state.** `paid_offline` requires an administrator
  and a recorded settlement, and submission can never produce it.
- **No self-assigned role.** There is no writable column for it.

## 12. Known limitations

- The RLS suites run against the shim, which emulates Supabase's `auth` schema.
  The shim is a faithful reproduction of `auth.uid()` and the role model, but it is
  not Supabase itself. Running the same suites against a real Supabase project is
  the final confirmation and is tracked in `KNOWN_ISSUES.md`.
- The concurrency proof uses a deliberately widened race window to make overlap
  certain. That is the correct way to test a lock — the alternative is a test whose
  result depends on machine speed — but it means the measured timings are not
  production timings.
- Supabase Storage bucket policies are not part of these migrations. They are
  configured in the Supabase dashboard and documented in `ARCHITECTURE.md` §12.
- Full-text search currently relies on a Postgres GIN index. If catalogue search
  needs ranking or typo tolerance beyond that, an external index will be required;
  it is not planned for any current phase.
